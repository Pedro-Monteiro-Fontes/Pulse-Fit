Projeto final: sistema web completo
Desenvolvimento Web · A2 · 3,5 pontos · grupos de até 4 pessoas



O que é
O grupo escolhe um sistema e constrói do banco à tela, com as mesmas ferramentas da Clínica Médica:https://github.com/douglasmeneses/clinicaMedica

Banco: PostgreSQL (no Docker) e Prisma
API: Node, Express e TypeScript
Validação: Zod, com os schemas num pacote shared usado pela API e pelo frontend
Documentação: Swagger em /docs
Frontend: React, Vite e TypeScript; Axios para chamar a API
Senha: bcrypt


O tema
Abaixo há 10 sugestões, já com as tabelas. O grupo pode pegar uma delas ou inventar a sua, sem precisar de aprovação, desde que cumpra os requisitos do banco.

Biblioteca: Autor, Livro, Leitor, Empréstimo (Livro → Autor; Empréstimo → Livro e Leitor)
Academia: Instrutor, Modalidade, Aluno, Matrícula (Modalidade → Instrutor; Matrícula → Aluno e Modalidade)
Oficina mecânica: Cliente, Veículo, Mecânico, Ordem de serviço (Veículo → Cliente; Ordem de serviço → Veículo e Mecânico)
Pet shop: Tutor, Animal, Serviço, Agendamento (Animal → Tutor; Agendamento → Animal e Serviço)
Cursos livres: Professor, Curso, Aluno, Inscrição (Curso → Professor; Inscrição → Aluno e Curso)
Locadora de carros: Categoria, Carro, Cliente, Locação (Carro → Categoria; Locação → Carro e Cliente)
Hotel: Tipo de quarto, Quarto, Hóspede, Reserva (Quarto → Tipo de quarto; Reserva → Quarto e Hóspede)
Eventos: Local, Evento, Participante, Inscrição (Evento → Local; Inscrição → Evento e Participante)
Estoque: Categoria, Produto, Fornecedor, Entrada (Produto → Categoria; Entrada → Produto e Fornecedor)
Salão de beleza: Cliente, Profissional, Serviço, Agendamento (Agendamento → Cliente, Profissional e Serviço)
"Livro → Autor" quer dizer que a tabela de livros tem a coluna autorId, como a consulta tem medicoId na clínica.



Requisitos


Organização
Mesma estrutura da clínica: um repositório com três pacotes (shared, api e frontend) e npm install na raiz instala tudo.
docker-compose.yml com o PostgreSQL ou banco local instalado na máquina.
api/.env.example com todas as variáveis que a API usa. O .env de verdade não vai para o GitHub.
Banco
Pelo menos 4 tabelas do sistema, todas ligadas a pelo menos uma outra por chave estrangeira (@relation no schema.prisma).
Pelo menos uma tabela ligada a duas outras, como a Consulta (que aponta para o médico e para o paciente).
Mais uma tabela de usuário, para o login (como o Secretario da clínica). Ela não conta nas 4.
Pelo menos um campo @unique além do id (CPF, e-mail, ISBN, placa...).
Migrations criadas com prisma migrate dev e guardadas no repositório.
Um seed que preenche todas as tabelas com dados de exemplo, incluindo um usuário para o professor entrar no sistema (o e-mail ou CPF e a senha ficam no README.md).
API
Organizada em camadas, como na clínica: routes → controllers → services → repositories.
CRUD completo das 4 tabelas do sistema: listar, buscar por id, criar, editar e remover (GET /livros, GET /livros/:id, POST /livros, PUT /livros/:id, DELETE /livros/:id).
Cadastro e login do usuário, com a senha guardada com bcrypt. A senha nunca aparece em nenhuma resposta da API.
Validação com Zod em todo POST e PUT, com os schemas no shared e o middleware validarBody (middlewares/validarSchema.ts). Dado inválido volta 400 com a mensagem de cada campo.
Status certos: 201 ao criar, 204 ao remover, 404 quando o id não existe, 400 para dado inválido. Valor repetido num campo @unique volta um erro com mensagem clara, não um 500.
A listagem da tabela ligada a duas outras traz os nomes das ligadas (include no Prisma), como a lista de consultas traz o nome do médico e do paciente.
Swagger em /docs com todas as rotas, os campos de entrada e as respostas.
Frontend
Telas de cadastro e login do usuário, validadas com os schemas do shared antes de enviar (o safeParse da aula 3).
Depois do login, uma Home com menu e uma tela para cada uma das 4 tabelas. Cada tela:
lista os registros vindos da API (useEffect);
cria e edita no mesmo modal;
remove pedindo confirmação.
No formulário da tabela ligada a outras, a escolha é por select preenchido pela API (como o médico e o paciente na nova consulta), nunca digitando o id.
Erros da API (validação, valor repetido) aparecem na tela, perto do campo ou num aviso.
Busca por texto em pelo menos uma das listas, com .filter (aula 4).
Todas as chamadas à API passam pelo Axios, num arquivo de serviço (como o services/api.ts).
npm run build -w api e npm run build -w frontend terminam sem erro.
A biblioteca de componentes é escolha do grupo. A clínica usa Mantine.

README.md
Link do vídeo, no começo.
Nome completo e RGM de cada integrante, e o que cada um fez.
Tema e a lista das tabelas, com as ligações entre elas.
Como rodar, do zero, passo a passo: subir o banco, criar o .env, rodar migrations e seed, subir a API e o frontend.
Usuário e senha do seed para entrar no sistema.

Vídeo: 1,0
O grupo grava um vídeo só, com a tela compartilhada, explicando o projeto. Não há apresentação em sala.

Regras do vídeo

Basta um integrante falar. O grupo escolhe quem apresenta.
A tela mostra o código o tempo todo em que ele está sendo explicado, com fonte grande o bastante para ler. Slide no lugar do código não conta.
Explicar é dizer o que cada trecho faz e por quê. Ler o código em voz alta, ou ler um texto pronto, não conta como explicação.
O vídeo é gravado com o código da entrega.
Link no YouTube (não listado) ou no Google Drive (qualquer pessoa com o link pode ver). Link que não abre vale 0.
Roteiro obrigatório, nesta ordem.

1. Abertura: Nome de cada integrante e o que cada um fez; o tema;
2. Banco: O schema.prisma: as tabelas, as chaves estrangeiras e o @unique; os dados do seed no banco
3. Sistema rodando: Cadastro, login, e numa das telas: criar, editar, remover e buscar. Um erro de validação aparecendo na tela
4. Caminho de um salvar: Do botão Salvar até o banco e de volta: componente, serviço com Axios, rota, validarBody, controller, service, repository, Prisma
5. Validação: O mesmo schema do shared no frontend e na API; pelo Swagger, a API recusando um dado inválido sem passar pela tela
6. Login: Onde entra o bcrypt, por que a senha não é guardada como foi digitada, e onde ela é tirada da resposta
Critérios

Partes 1 e 3: integrantes e sistema rodando: 0,25
Parte 2: banco explicado: 0,25
Parte 4: caminho do salvar explicado em todas as camadas: 0,25
Partes 5 e 6: validação e login explicados: 0,25
